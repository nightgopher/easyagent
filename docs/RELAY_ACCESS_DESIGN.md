# 远程访问中继设计（扫码即连）

状态：设计评审稿，尚未实现（2026-11-01）。本文是「手机扫码即跨网连接桌面 EasyAgent」的主设计，实现拆分见里程碑。关联文档：[IOS_CLIENT_DESIGN.md](IOS_CLIENT_DESIGN.md)（其 M1 配对令牌是本设计的基础；本文补充中继传输与设备凭证约束）、[SECURITY_MODEL.md](SECURITY_MODEL.md)。

## 背景与动机

iOS 设计文档 v1 的跨网方案是 Tailscale / 反向代理，自用可行，C 端不可行。2026-11-01 实测自家环境（tailnet `hwj`，Headscale 部署首尔）：

- `MappingVariesByDestIP: true`（对称 NAT），`tailscale ping` 报 `direct connection not established`
- MacBook ↔ mini 全部流量绕行 DERP(hkg)，RTT 125-170ms
- 这次观测说明该测试环境无法可靠直连，不能据此推断所有家宽或办公网的打洞成功率。面向普通用户，需要提供不依赖用户配置 VPN 或反向代理的连接方式。

因此 C 端需要「主机主动连出 + 运营方中继」模式。参考实现：[yetone/alma-relay](https://github.com/yetone/alma-relay)（MIT）——桌面出站 WebSocket 到中继、手机经中继转发、端到端加密、扫码配对，可参考其会话注册和 WebSocket hibernation。本文采用下述钉扎 TLS 方案，不复用其应用层 ECDH+AES-GCM 协议。

## 目标与非目标

目标：

- 手机装 App → 扫桌面端二维码 → 跨网连接，全程零网络配置（无 VPN、无公网 IP；前提是两端网络允许出站 HTTPS/WSS 到中继）
- 业务内容端到端加密：中继只见密文和路由元数据；在正确校验钉扎指纹与主机认证的前提下，运营方无法读取或伪造业务内容
- 复用既有 `serve` 业务 HTTP/WebSocket 协议、Owner 门禁和 API Key 机制；需要新增配对与设备认证接口，不能将传输透明等同于服务端零改动

非目标（首版）：

- 不做账号体系与计费（v2 订阅另行设计，参考 IOS_CLIENT_DESIGN v2 规划）
- 不做 P2P/NAT 打洞；同局域网直连优化列为后续（二维码预留局域网地址字段）
- 不做 APNs 推送（后续里程碑，依赖中继在线状态，见开放问题）
- 不做一台主机多手机共享、自托管中继分发

## 总体架构

```
桌面 EasyAgent                       中继（我们运营，HK）              手机 App
┌─────────────────┐    出站 WSS     ┌──────────────┐    WSS     ┌──────────────┐
│ serve + 配对认证 │◄─隧道(穿NAT)──  │ 会话注册表     │◄─隧道──────│ 既有 Backend  │
│ relay-client(新) │───────────────►│ 密文帧转发     │───────────►│ (协议不变)    │
│  └ 本地TLS壳(新)  │               │ 在线状态      │            │              │
└─────────────────┘                └──────────────┘            └──────────────┘
        └──────────── E2E：TLS with 证书钉扎，中继只见密文 ────────────┘
```

三个新组件，各角色边界：

| 组件 | 位置 | 职责 | 明确不做 |
|---|---|---|---|
| relay-client | 桌面（`internal/relay`） | 出站 WSS、重连保活、把隧道桥接为本地 TCP | 不改 serve 协议 |
| 中继 | 独立 `cmd/easyagent-relay` 单二进制 | 注册、路由、帧转发、在线状态 | 不解析不落盘任何载荷 |
| 手机端配对 | iOS / Android 既有主机管理 | 扫码、钉扎证书、按 transport 连接 | 不新增业务协议 |

关键决策 1：**隧道内是透明 TCP 字节流**（每条手机连接 = 一条隧道内虚拟连接，必须先交给主机 TLS 终止点，再转发到 `127.0.0.1:<serve端口>`）。中继不能选择转发目标或直接连接未加密的 serve 端口。既有业务 HTTP/WebSocket 语义保持不变，配对与设备认证作为新增控制接口接入。

关键决策 2：**E2E 用标准 TLS + 证书钉扎，不自研应用层加密**。配对时桌面生成自签名证书（长期密钥），二维码携带证书公钥指纹；relay-client 在本地起 TLS 壳（`crypto/tls` 监听 → 设备认证 → 转发 127.0.0.1:serve），手机按钉扎指纹直连。中继只见 TLS 密文。不用 alma-relay 的应用层 ECDH+AES-GCM 方案——我们的流量本来就是标准 HTTPS，让 stdlib 做加密，避免在两端各加一层自研密码学（理由：实现与审计成本；若后续需要中继侧可见的元数据路由再评估）。

## 配对协议（扫码即连）

二维码内容（JSON，一次性令牌 5 分钟有效、单次使用）：

```json
{
  "v": 1,
  "relay_url": "wss://relay.example.com",
  "route_id": "r_...",
  "host_pubkey_fp": "sha256:...",
  "pair_token": "pt_...",
  "lan_addr": "192.168.x.x:8443"
}
```

`host_pubkey_fp` 固定为 TLS 公钥 SubjectPublicKeyInfo DER 的 SHA-256，以 Base64 编码并加 `sha256:` 前缀，两端使用同一规范校验。

时序：

1. 桌面开启「远程访问」→ 向中继注册，取得公开的 route_id 和独立的主机隧道凭证 → 用该凭证认证 `GET /host`，保持出站 WSS。route_id 仅用于路由，不能证明主机身份。
2. 桌面通过已认证的本机 Owner 控制入口调用 `POST /pair/qr`，由主机生成高熵 pair_token，并记录有效期与单次使用状态；渲染二维码。远程未配对设备不能自行生成配对令牌。
3. 手机扫码 → 仅凭路由信息连接中继 WSS → 经透明隧道与主机 TLS 终止点握手，先校验证书公钥指纹等于二维码中的 `host_pubkey_fp`。校验失败即断开，不回退到明文或系统默认信任。
4. 手机只在上述已校验的端到端 TLS 内，将 pair_token 发送给主机配对接口。主机检查有效期并原子消费令牌，再颁发可单独撤销的设备凭证。令牌不得出现在中继 URL、握手参数、状态接口或日志中；中继不参与配对授权。
5. 手机保存 relay_url、route_id、钉扎指纹，并将设备凭证存入系统安全存储。主机保存对应凭证的安全校验材料与撤销状态。后续连接仍须先钉扎 TLS，再提交设备凭证；不凭 route_id 或已知指纹直接取得 API 权限。
6. 主机在转发到本地 serve 前强制验证设备凭证，并将其接入既有 Owner/API Key 授权边界。不得因转发来源为 loopback 而放行。禁用远程访问、撤销设备或轮换凭证应立即阻止新请求，并关闭相应存量连接。

`lan_addr` 仅为后续局域网直连预留；将来实现时也必须指向相同的钉扎 TLS 与设备认证入口，不能作为明文 HTTP 回退地址。首版不实现自动选择逻辑。

## 中继服务

形态：Go 单二进制 `cmd/easyagent-relay`（与仓库技术栈一致，便于复用团队运维；接口极小，后续如需弹性可移植 Workers）。首选部署 HK，最终根据两端实测 RTT、稳定性与成本决定；单次延迟观测不构成地域或用户体验保证，随仓库附 `deploy/` systemd 模板与部署文档。

端点（全部 WSS/HTTPS，无业务语义）：

| 端点 | 方向 | 作用 |
|---|---|---|
| `POST /register` | 桌面 | 携带防滥用注册凭证，取得 route_id 与独立的主机隧道凭证 |
| `GET /host?route_id=` | 桌面 | 使用授权头中的主机隧道凭证认证后升级 WSS，30s ping/pong 保活 |
| `GET /client?route_id=` | 手机 | 仅建立字节隧道；不接收 pair_token、设备凭证或 Owner API Key |
| `GET /status?route_id=` | 手机 | 受限的在线状态，须防枚举和限流；不构成业务授权 |

转发模型：帧 `{type: data | open | close | ping}`，`data` 为不透明二进制（TLS 密文），一一映射到「手机虚拟连接 ↔ 主机 TLS 终止点」。虚拟连接 ID 必须隔离，限制帧大小、缓冲与并发并提供背压，关闭后释放资源。在线连接表可在内存中重建；route_id 与主机隧道凭证的注册/恢复必须另有认证持久化方案，不能在重启后允许任意客户端抢占已有 route_id。

防滥用（C 端开放前的最小集）：注册密钥灰度发放、单 route_id 并发连接上限、单连接带宽限制、帧与总缓冲上限、握手超时。注册密钥机制参考 alma-relay 的 `RELAY_REGISTRATION_KEY`。这些中继侧凭证仅用于路由占有和防滥用，不得授予 EasyAgent 业务访问权，也不得复用主机设备凭证或 API Key。

## 手机端改动

- 主机模型增加 `transport: direct | relay`；扫码后自动创建 relay 主机，无需用户理解地址概念
- 连接层：relay 主机 = 连中继 WSS + 钉扎 TLS；既有流式对话 / 工具审批 / 会话同步协议不变（见 IOS_CLIENT_DESIGN「与服务端的契约」）
- Android 与 iOS 实现相同的配对、钉扎与认证契约，分别接入各自的连接层

## 安全模型

在 [SECURITY_MODEL.md](SECURITY_MODEL.md) 基础上新增以下性质：

- pair_token 是有效期内的配对授权；泄漏后攻击者仍可能抢先配对。必须使用系统随机源生成、短时有效、原子单次消费、限制失败次数并禁止写日志；二维码只能展示给用户明确选择的设备
- 主机私钥仅存桌面（文件权限 0600 / Keychain），公钥指纹经二维码带外传递，TOFU 绑定
- 中继只见 TLS 密文与路由元数据（route_id、连接时长、流量体积）；不能承诺匿名性、可用性或隐藏流量特征。恶意中继仍能断连、延迟或重放帧，业务认证与 TLS 必须拒绝伪造/重放的授权
- Owner 门禁与 API Key 沿用既有机制；主机必须阻止未认证隧道利用 loopback 默认信任访问业务 API。配对接口是限定能力的例外，仅可消费令牌并签发设备凭证，不能调用工具或读取会话
- 首版必须提供取消配对、设备凭证撤销和关闭远程访问能力；主机公钥变化必须重新扫码确认，不能自动更新钉扎值

## 里程碑（实现拆分）

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 | Owner 保护的二维码生成、主机配对接口、设备凭证存储与撤销 | 过期/重复/并发消费被拒；未配对请求无业务权限，撤销立即生效 |
| M2 | `cmd/easyagent-relay`、注册/重连认证、流控与部署模板 | 两台 NAT 后设备互通；重启不能抢占路由，跨连接帧不能串流 |
| M3 | 桌面 relay-client（WSS + 重连 + 钉扎 TLS 与认证桥接） | 正常业务 API 全通；错误指纹、明文隧道、无效设备凭证均被拒，无法借 loopback 绕过门禁 |
| M4 | 手机扫码配对闭环（iOS 并入其 M1）与两端安全存储 | 在指定测试网络下扫码到流式对话目标 30 秒；中继日志/抓包不含配对和设备凭证，断网重连仍需认证 |
| M5（后续） | APNs、局域网直连、多设备管理、多区域中继 | 另行设计；基本凭证撤销不得推迟到此阶段 |

依赖顺序：M1 → M2 → M3 → M4，M2/M3 可并行开发（先以本地回环联调）。

## 开放问题

1. 中继域名与 TLS 证书自动化（Caddy / certbot 选型），多区域路由策略
2. 带宽成本核算与 v2 订阅定价（中继是唯一持续成本，也是付费点）
3. 是否支持用户自托管中继并填入自定义 relay_url（与官方中继并存，影响配对二维码设计与防滥用模型）
4. APNs：推送证书申请流程与长任务完成通知的触发点（依赖 M2 在线状态接口）
