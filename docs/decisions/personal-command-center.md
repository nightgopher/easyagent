# 个人指挥台：目标、结果与设备调度

状态：方向讨论，尚未实施（2026-11-06）。本文记录产品形态的取舍，以及动手前需要验证的事项。交互原型见 [prototypes/personal-command-center](../prototypes/personal-command-center/README.md)。

## 背景

EasyAgent 已经具备通用 agent 的能力：对话、工具、会话、MCP、Skills，以及桌面、Android、Web、TUI、飞书等多个入口。但在日常使用中，编程有 Codex、Claude Code、zcode，调研有 GPT、豆包，这些单点工具都比 EasyAgent 强。真正缺少的，是一个能长期**统领个人工作**的层：

- **跨工具**：同一件事会先后用好几个工具来做，每个工具都只认识它自己的会话。
- **跨时间**：工具关掉之后，没有任何东西还在记着「这件事做到哪了」。
- **跨设备**：日常使用三台开发机（三种系统）和两台 Linux 服务器，机器之间通过自建的 Tailscale 直接互通。哪台机器在做什么、做到一半该怎么换到另一台，全靠人自己记。

## 定位

EasyAgent 做**个人指挥台**：负责调度和收集结果，不跟单点工具比谁更强。

- **不拆出新产品**。通用 agent 继续维护，它既是指挥台里最常用的执行者，也是其他功能共用的基础：会话、工具、审批、常驻主机、手机和飞书接入。
- **不做「记住一切」的 IM 型 agent**。这类产品把状态藏在模型的记忆里，把所有工作塞进同一条无限长的对话，结果是记忆越来越乱、上下文越来越长。指挥台把状态放在**用户看得见、能修改的界面对象上**。
- **不重做工作流引擎**。2026-10 下线的动态工作流和 YAML 流水线（见 [workflow-engine](workflow-engine.md)）解决的是「怎么编排步骤」；这里要解决的是「事情和结果的状态」，以及「活在哪台机器上做」。

## 核心模型：目标 → 结果，过程不管

| 层 | 类比 | 内容 | 指挥台是否管理 |
|---|---|---|---|
| 空间 | 仓库 | 一件长期的事：一个项目、求职、学一门语言 | 管理 |
| 目标 | issue | 要什么结果、完成标准、当前状态、截止时间 | **核心** |
| 结果 | PR / 交付物 | 能验收的东西：PR、分支、提交、报告、文档、决定 | **核心** |
| 过程 | 本地的开发操作 | 在 Codex、Claude Code、zcode、EasyAgent 里开的会话 | 不管理，只读关联，默认折叠 |

开多少个会话、在哪个工具里开，都属于过程。指挥台只关心目标有没有被结果关闭，就像 GitHub 不关心开发者本地用的是什么编辑器。

**结果如何挂到目标上**

- 代码类：分支名和 PR 描述约定写目标编号（如分支 `goal/12-…`、PR 里写 `Closes #12`）；无法识别的分支作为「未归属的结果」，由用户挂到某个目标或新建目标。
- 非代码类：拖入文件、粘贴链接，或者在任意会话里说一句「这是 #12 的结果」。
- 第一版只依赖 git 和手动添加；解析各家工具的本地会话记录放到后面，避免绑定任何一家的内部格式。

**上下文怎么传给其他工具**

开工时生成一份「开工包」：目标、完成标准、已有结果的摘要、空间笔记，再加上分支约定。**不带任何历史会话。** 每次开工的上下文都是有边界的，不会越积越长。

**记忆放在可见的对象上**

空间笔记、目标、结果就是记忆。agent 只能**提议**修改，用户在界面上一键确认后才会写入，交互和现在的工具审批一致。全局只保留一份很薄的个人档案（现在的 `internal/profile`）。

## 与现有界面的关系

| 现在 | 之后 |
|---|---|
| 会话列表 | 不属于任何目标的会话放进「随手聊」，用法不变 |
| 会话页（流式输出、工具、审批） | 执行者是 EasyAgent 时，「过程」就是这个页面 |
| 工具审批 | 也进入收件箱，手机和飞书都能处理 |
| `/loop`、知识库、profile | 分别成为目标或空间上的定时任务、空间资料、个人档案 |
| 新增 | 收件箱首页、目标与结果、设备 |

指挥台的状态和调度逻辑放在 `internal/`（应用层）。`sdk/` 保持零领域知识；等执行者接口稳定后，再评估是否抽象进 SDK。

## 设备与中枢

**中枢**保存目标、结果和设备注册表，负责分配任务和交接。手机和飞书只连接中枢。

- **节点**：每台机器运行 `easyagent serve`，监听在 Tailscale 地址上，由中枢直接访问（机器之间已经互通，不需要反向连接或内网穿透）。节点额外上报自己的能力：操作系统、已安装的工具、有哪些仓库、是否空闲。`sdk/operations` 的 SSH 后端也可以走 Tailscale。
- **鉴权**：Tailscale 的访问控制决定谁能连到谁，EasyAgent 现有的服务令牌决定谁能派活；跨机器执行同样经过审批。
- **中枢放在哪**：倾向放在现在的迷你主机上，因为飞书桥接、配对、手机连接、会话数据都已经在那里；两台服务器专门承担长任务。需要调整两点：
  - 中枢改为跟随正式 Release 升级，不再每个 main 提交都自动部署（见 [迷你主机部署](../MINI_DEPLOY.md)），以免一个坏提交影响所有设备的状态；
  - 中枢的数据定期备份到一台服务器上。中枢是一个角色，状态放在单个目录里，可以迁移到其他机器。

  如果服务器是云主机，比家里的网络和供电更稳定，就反过来放在服务器上。

三种跨设备场景只需要两个操作：

| 场景 | 操作 |
|---|---|
| 同一件事在几台开发机之间换着做 | **交接**：未提交的改动推成 WIP 提交，由当前工具写一份交接说明（进度 / 下一步 / 需要注意的地方），作为结果挂到目标上；接手方带着开工包和交接说明开始 |
| 在开发机上开头，长任务放到服务器上跑 | **开工**时选择服务器 |
| 某些步骤只能在特定系统上做（打包、兼容性测试） | 在完成标准上标注所需设备，开工时自动推荐对应机器 |

git 负责搬运代码，目标负责搬运上下文，整个过程不同步会话。

## 执行：驱动真实应用

**默认驱动用户已登录的真实应用，不以无头模式或模型 API 为主。** 原因有两个：

1. `claude -p`、`codex exec` 这类无头运行出问题时，人很难接着处理；而会话在 Codex 或 Claude 桌面版里，打开应用就能直接接手。
2. 对话记录属于用户在该产品里的账号。比如通过 API 去「问豆包」，这段对话就不会出现在用户的豆包历史里，豆包对用户的记忆和后续追问也就断了。

**桌面端**：[vercel-labs/agent-desktop](https://github.com/vercel-labs/agent-desktop)（Apache-2.0，2026-10 发布）读取系统的无障碍树（macOS AX、Windows UI Automation、Linux AT-SPI），给界面元素分配稳定的引用，默认在后台操作、不抢焦点，并提供 MCP 模式。它可以作为现有 `internal/computer`（仅支持 macOS、基于截图）的跨平台后端。

- GUI 只自动化开头的几个动作：打开项目或 worktree、新建对话、粘贴开工包、发送。
- 状态和结果仍然从 git 和应用的本地记录读取，不解析界面。界面操作越少，应用改版时越不容易坏。
- 没有桌面环境的 Linux 服务器继续使用 CLI 无头模式，作为明确的兜底方案。

**手机端**：[wangzan101/Mika](https://github.com/wangzan101/Mika)（Apache-2.0，Kotlin + Compose，与 `mobile-native/` 技术栈相同）在隐藏的后台屏幕上操作 App，通过无线调试获得控制权限，涉及支付、登录、验证码时交还给用户，也支持从电脑通过 CLI 或 MCP 派任务。

## 手机端

- **只做决定，不做实现**：验收、批准、接手、派活，每件事都能在一屏内处理完。目标页只看进度和结果，不显示会话。
- **只连接中枢**：现在「保存并切换多台主机」的列表，变成「设备」页签。会话和审批能力原样保留在「随手聊」里。
- **几乎唯一的入口**：除微信、支付宝、银行这类应用之外，日常的「问」和「做」都从 EasyAgent 发起。
  - **问**：同一个输入框，选择问 EasyAgent、豆包、元宝、Kimi……EasyAgent 在后台打开对应 App，发送问题，等回答完成后用 App 自带的「复制」按钮取回答案。对话同时留在用户账号里。如果某个产品的网页版和 App 共享对话记录，也可以在常驻机器上用已登录的浏览器（agent-browser）来做，这样不受手机无线调试断开的影响。
  - **做**：外卖、查票、在某个 App 里操作，采用 Mika 的后台屏幕方式。手机作为设备列表里的一台设备，中枢可以给它派任务，结果进入收件箱。
  - **记**：右下角「随手记」，由 EasyAgent 判断这句话是新目标、某个目标的补充还是一个问题，用户确认后归档。

## 风险

- Codex 和 Claude 桌面版很可能是 Electron 应用，暴露的无障碍树可能不完整；agent-desktop 对 Electron 有走 DevTools 端口的补充方案，但还没有针对这两个应用的公开案例。
- 锁屏或屏幕休眠时，GUI 驱动是否还能工作，尚未确认。
- Linux 的 Wayland 环境不接受指针输入；Codex 和 Claude 桌面版在 Linux 上是否有官方版本，尚未确认。
- 应用改版会导致适配失效，所以每个应用的适配只覆盖少数几个固定动作。
- 手机重启或更换 Wi-Fi 后，系统会关闭无线调试；Android 14 及以上体验较好。
- 自动操作第三方 App 可能违反其用户协议；屏幕内容会发送给模型服务商。

## 验证计划

先做两个小验证，通过之后再动产品代码。

**验证 A：桌面驱动**（在 mac 上进行）

用 agent-desktop 驱动 Codex 桌面版，依次完成：打开仓库 → 新建对话 → 粘贴开工包 → 发送，然后从 git 读到它产出的提交。

- 通过标准：连续成功 5 次；中途人能直接在应用里接手；对 Claude 桌面版重复一遍。

**验证 B：手机自动化**

在手机上安装 Mika，由中枢派发一个「问豆包某个问题」的任务。

- 通过标准：回答完整回到 EasyAgent；这段对话出现在豆包账号的历史记录里；手机重启后仍能继续派发任务。
- 如果豆包网页版和 App 共享记录，同时用网页版做对照，比较两者的稳定性。

**之后的阶段**

1. 中枢：目标与结果的数据模型、通过 git 发现结果、收件箱、开工包。
2. 设备：节点能力上报、开工时选择设备、交接与接手。
3. 手机：收件箱 / 目标 / 设备页签，随手记，问与做。

## 待定问题

- 中枢最终放在迷你主机还是服务器上；迷你主机是否已加入 Tailscale。
- 豆包等产品的网页版和 App 是否共享对话记录。
- Mika 采用外部集成（CLI / MCP）还是合入 `mobile-native/`。Apache-2.0 允许合入，但需保留 NOTICE。
- 交接说明由谁生成：由交出方的工具生成（需要驱动它），还是由 EasyAgent 读取 git 差异后生成。
